# 记忆陪伴优先的专属虚拟女友设计

**目标**：在现有 1.0 日记产品基础上，升级为“每个用户拥有自己的专属虚拟女友，并且她会持续记住这个用户”的关系型陪伴产品。

**范围**：
- Web 端首发产品体验
- 专属女友匹配开场
- 基于日记的记忆采集与回响
- 关系阶段成长与隐藏解锁
- 用户轻反馈与阶段性校准
- 支撑上述体验的关系与记忆架构

**不包含**：
- 首发开放聊天系统
- 多角色同时切换
- Mobile App 同步改造
- 复杂多 Agent 编排
- 全量向量数据库优先的重 RAG 架构

---

## 1. 背景与产品判断

当前 1.0 已具备几个关键基础：

1. 已有“请她写”与“我来写”两类内容入口。
2. 已有日记生成、图片生成、语音生成和一定的记忆召回能力。
3. Web 前端已默认依赖后端 API 与生成任务系统。
4. 当前“女友”仍偏单一公共角色，记忆沉淀还不是真正的“每用户专属关系”。

本轮升级的关键判断是：

- 先不把聊天当首发核心。
- 先把“她居然记得这个”做成产品主体验。
- 用“专属匹配 + 记忆回响 + 关系成长”形成留存闭环。

一句话定义本轮产品：

`不是生成一个虚拟女友，而是让用户遇见一个会长期记住他的专属关系对象。`

---

## 2. 产品目标

### 核心目标

1. 每个用户拥有独立的专属女友档案，不再共享单一公共人设。
2. 用户第一次进入产品时，通过沉浸式开场逐步“唤醒”她，而不是看到干巴巴的问卷或首页。
3. 日记成为首发阶段最主要的关系输入载体。
4. 新生成的内容必须能自然体现“记忆回响”，而不是每次像重新生成新角色。
5. 用户可以逐步塑造她，但不破坏“她是先被匹配出来的”这一体验。
6. 关系推进应有成就感，但前台表达要克制，不做重数值游戏化。

### 成功信号

1. 用户能明确感知到“她记得我”。
2. 用户愿意持续记录，而不是只在第一次匹配时停留。
3. 用户感知到“她越来越对味”。
4. 关系阶段变化能通过内容行为而不是口号体现。

---

## 3. 核心爽点与产品主张

本产品的主爽点排序如下：

1. `被记住`
她记得用户说过的话、偏好、脆弱点、过去的细节，并在未来主动提起。

2. `专属感`
她不是平台共享角色，而是只属于当前用户的关系对象。

3. `被理解后的匹配感`
不是直接捏一个角色，而是先被理解，再遇见她。

4. `关系成长感`
她会随着相处发生变化，越来越贴近用户的想象与需求。

5. `隐藏解锁带来的成就感`
某些变化不会被系统大声宣布，而是以轻提示或内容行为突然出现。

---

## 4. 首发产品主线

本轮首发采用：

`记忆陪伴优先，匹配仪式做入口，关系成长做放大器。`

也就是：

- 入口靠沉浸式匹配开场建立命中感。
- 核心留存靠日记驱动的记忆回响。
- 中期留存靠关系阶段变化与隐藏解锁。

不采用的首发路线：

- 纯聊天陪伴优先
- 纯角色捏脸/DIY 优先
- 重数值养成优先

---

## 5. 用户旅程

## 5.1 第一次进入

用户第一次进入产品，不直接进入主页，而是先进入一段沉浸式开场。

这个开场是：

- 朦胧梦境感
- 安静、低饱和、克制
- 画面中有一个女生在缓慢呼吸
- 她一开始就微微睁眼，但并未完全清醒
- 用户通过回答问题逐步让她变得更具体

这个过程不是“填写表单”，而是“唤醒她”。

## 5.2 快速得到她的初版

匹配问答采用：

- 真实模式为主
- 幻想模式为辅
- 由浅入深
- 随时可跳过
- 3 到 5 题先给出初版结果

初版结果不是完整终局，而是：

- 她的人格底色
- 她的陪伴方式
- 她与用户的初始距离感
- 她当前的主动性和表达风格

## 5.3 开始记录

用户的首发主互动不是聊天，而是：

- 写日记
- 记录片段
- 表达心情、经历、偏好和关系投射

这些内容会被系统转化为“可记忆、可回响、可塑造关系”的输入。

## 5.4 记忆回响开始发生

随着日记增加，她会在后续内容中开始回响过去：

- 日记里自然提起旧事
- 首页出现轻量回响
- 语音出现连续性与熟悉感

用户由此感受到，她不是固定模板，而是在延续这段关系。

## 5.5 关系成长

随着持续记录、真实输入和反馈累积，关系阶段发生变化。

用户感受到的不是属性变化，而是：

- 她更会主动靠近
- 她更自然地提起过去
- 她更少客套
- 她越来越懂用户的情绪节奏

## 5.6 轻量纠偏与阶段性校准

用户不是通过大设置面板调参，而是通过：

- 单次内容后的轻反馈
- 周期性小校准

逐步让她越来越“对味”。

## 5.7 隐藏解锁

某些成长不通过单独任务页展示，而是在内容中被轻轻提示：

- 她第一次主动提起一段旧事
- 她第一次换更亲近的称呼
- 她开始用更懂用户的方式安慰

---

## 6. 前端体验设计

## 6.1 首发界面原则

Web 端首发不强调“功能导航感”，而强调“陪伴关系感”。

客户端层的主要职责是：

- 承载沉浸式开场
- 提供日记记录入口
- 展示首页轻回响
- 提供低存在感反馈入口
- 以嵌入式方式展示关系提示

## 6.2 匹配开场

匹配开场不是主页上的功能模块，而是首进时的开场仪式。

设计要求：

1. 画面中出现女生，她微微睁眼，带有呼吸感。
2. 问题像靠近，不像测试。
3. 前几题偏气质与距离感，后几题才逐步触碰真实经历。
4. 用户回答得越多，她越具体；跳过不会阻塞流程。
5. 不在开场中暴露系统参数和复杂设置。

## 6.3 日记页

日记页是首发主战场，承载：

- 用户输入
- 内容生成
- 记忆回响
- 轻提示解锁
- 轻反馈纠偏

解锁提示与关系提示的理想形态是：

- 灰色弱提示文案
- 嵌入在写作或生成后的内容附近
- 不做独立入口

## 6.4 首页

首页不承担复杂成长看板，而承担轻量回响：

- 她今天想起了什么
- 她最近更懂了什么
- 某个细节被她记住了

首页是“关系氛围面”，不是“数据后台”。

## 6.5 反馈纠偏

反馈纠偏是次要功能，不应显眼。

首发入口优先放在：

- 日记生成后的小反馈
- 偶发的阶段性校准

不建议首发做成：

- 高曝光设置页
- 大量可见参数面板

---

## 7. 匹配机制设计

## 7.1 首发模式

首发采用：

`真实模式为主，幻想模式为辅`

真实模式主要用于建立：

- 用户的关系经验
- 审美偏好
- 亲密边界
- 情感需求
- 对理想伴侣的投射

幻想模式主要用于补充：

- 理想外形
- 理想音色
- 理想氛围
- 用户不愿回答过深问题时的低敏替代输入

## 7.2 问题路径

问题顺序采用：

1. 低压力问题
2. 气质偏好问题
3. 互动偏好问题
4. 少量真实经历问题
5. 可选更深层问题

设计原则：

- 由浅入深
- 允许跳过
- 明示“了解越深，她越贴近你”

## 7.3 初版输出

初版匹配结果不直接输出一段固定文案，而是生成一套可持续生效的关系参数：

- 人格底色
- 主动程度
- 亲密节奏
- 表达风格
- 回忆频率倾向
- 现实感 / 幻想感权重

---

## 8. 角色塑造机制

## 8.1 塑造分层

“她的性格”不应只是一段人设描述，而应拆成 5 层：

1. `人格底色`
决定她总体是什么样的人。

2. `情感需求偏好`
决定她更倾向于怎样爱和陪伴用户。

3. `亲密边界`
决定她靠近的速度、主动程度和追问深度。

4. `表达风格`
决定她说话的口气、温度、成熟度与俏皮度。

5. `记忆唤回策略`
决定她回响过去的频率和方式。

## 8.2 塑造来源

她的形成采用：

`初始匹配定 60%，后续相处与反馈继续塑造。`

也就是：

- 问答决定初版底色
- 日记内容决定她能记住什么
- 用户反馈决定她怎样越来越贴近

---

## 9. 记忆系统设计

## 9.1 首发记忆来源

首发阶段，记忆主要来源于日记与补充问答，不依赖聊天。

可采集的记忆类型包括：

- 具体事件
- 情绪波动
- 偏好表达
- 关系观
- 脆弱点
- 人生经历片段
- 可回响的细节

## 9.2 两类记忆

记忆系统建议拆成两类：

### 结构化记忆

适合长期稳定存储：

- 偏好
- 边界
- 审美倾向
- 重要日期
- 关系标签
- 当前关系状态

### 片段记忆

适合未来内容回响：

- 某次真实经历
- 某句情绪表达
- 某个可被再次提起的细节

## 9.3 记忆不是全文缓存

首发不建议简单保存全文后直接塞回 prompt。

需要从文本里提炼“值得被她记住的点”，否则：

- 上下文会膨胀
- 回响会不稳定
- 很难控制内容质量

---

## 10. 高质量真实输入判断

## 10.1 判断目标

系统不直接判断“用户真不真诚”，而判断：

`这段输入有没有提供可沉淀的关系信息。`

## 10.2 三个核心信号

### 具体度

是否包含：

- 明确场景
- 明确人物
- 明确时间
- 明确情绪原因

### 自我暴露度

是否透露：

- 偏好
- 脆弱点
- 恋爱经验
- 关系需求
- 真实想法

### 可回响性

是否包含未来适合被提起的记忆点，例如：

- “我最怕别人突然冷下来”
- “下雨天我会特别低落”
- “我其实不喜欢麻烦别人”

## 10.3 首发实现原则

首发采用：

`规则优先，模型辅助`

也就是：

- 规则负责稳定判断信息密度
- 模型负责抽取最值得记住的点
- 不让模型单独决定关系推进分数

## 10.4 激励方式

首发采用 `半显性激励`。

也就是用户会收到正反馈，但看不到冷冰冰的分值：

- “你刚刚提到的那段经历，让她更了解你的边界。”
- “这次分享让她更容易记住你的情绪节奏。”
- “你们之间的默契，正在变得更具体。”

---

## 11. 记忆回响设计

## 11.1 首发回响载体

首发以 `日记内容` 为主要回响载体。

辅助载体为：

- 首页轻回响
- 语音的连续性

## 11.2 回响原则

回响必须：

- 自然
- 具体
- 不像系统在引用数据库
- 更像她突然想起了什么

## 11.3 典型回响形态

1. 日记里自然提起之前的某个细节。
2. 她开始把多个时间点的情绪联系起来。
3. 她用已经形成的默契称呼或语感靠近用户。
4. 她在安慰或陪伴时带入过去的了解。

---

## 12. 关系成长与可视化

## 12.1 外显原则

首发不做重属性条，而采用：

- 关系阶段变化
- 隐藏解锁事件提示

属性存在于后台，但前台主打“关系变化被感知”。

## 12.2 后台成长维度

首发建议控制在少数关键维度：

- 亲近度
- 主动性
- 回响能力
- 边界贴合度
- 风格收敛度

## 12.3 前台成长感受

用户应该感受到：

- 她开始更主动
- 她开始更会记住
- 她越来越像懂自己的人
- 她开始用固定方式陪伴自己

## 12.4 阶段不是标题，而是行为切换

进入更高阶段后，至少会变化：

- 提起旧事的自然度
- 主动开口的频率
- 对情绪的判断深度
- 称呼的亲密度
- 安慰与陪伴的方式

如果只是标题变化，没有行为变化，则阶段系统无意义。

## 12.5 隐藏解锁

隐藏解锁的理想形态包括：

- 她第一次主动提起一段旧事
- 她第一次换更亲近的称呼
- 她第一次开始替用户总结情绪
- 她第一次形成固定陪伴习惯

解锁提示仅以灰色弱提示出现，不做单独功能入口。

---

## 13. 反馈与阶段性校准

## 13.1 反馈入口

首发以 `互动后反馈` 为主，`阶段性校准` 为辅。

不以显眼设置页为主要调教入口。

## 13.2 反馈目标

用户反馈主要调的是：

- 主动程度
- 亲密节奏
- 表达风格
- 回忆频率
- 追问深度
- 现实感与幻想感的权重

## 13.3 反馈表达

用户不需要理解参数，只需要表达喜欢或不喜欢。

例如：

- 更喜欢她这样说
- 希望她别这么主动
- 多记住这种事
- 这种感觉不太对

系统再把这些反馈映射到底层关系参数。

---

## 14. 架构设计

## 14.1 总体原则

本轮不推翻现有 1.0，而是在已有 `Web 前端 + 后端 API + 生成任务` 之上长出关系系统。

## 14.2 分层

### 客户端层

负责：

- 沉浸式开场
- 日记输入
- 首页轻回响
- 低存在感反馈入口
- 嵌入式关系提示

不负责：

- 决定她的性格
- 决定回忆什么
- 决定阶段如何变化

### 应用 API 层

负责业务读写：

- 用户
- 专属角色
- 关系状态
- 记忆条目
- 日记记录
- 反馈记录
- 解锁事件

### 生成任务层

继续承接异步生成任务：

- 日记生成
- 语音生成
- 图片生成
- 未来的回响生成或阶段性内容生成

### 关系引擎层

负责维护：

- 当前角色底色
- 关系阶段
- 主动性与边界节奏
- 解锁状态
- 风格收敛状态

### 记忆系统层

负责：

- 结构化记忆存储
- 片段记忆提炼与检索
- 回响候选内容的供给

### 模型编排层

负责把：

- 当前输入
- 关系状态
- 召回记忆
- 最近反馈

组合成这一次生成所需的上下文。

## 15. 数据模型建议

首发至少需要以下核心实体：

1. `User`
2. `CompanionProfile`
3. `RelationshipState`
4. `OnboardingAnswer`
5. `MemoryItem`
6. `JournalEntry`
7. `InteractionFeedback`
8. `UnlockEvent`

### User

保存账号身份与基础用户信息。

### CompanionProfile

保存用户专属女友的初始匹配结果与当前人格收敛参数。

### RelationshipState

保存当前阶段、主动性、亲近度、边界贴合度、回响能力等状态。

### OnboardingAnswer

保存匹配开场中的问题回答与后续补充问答。

### MemoryItem

保存结构化记忆与片段记忆，需包含类型、权重、可回响性和来源。

### JournalEntry

保存用户输入、生成结果与关联记忆。

### InteractionFeedback

保存单次轻反馈和阶段性校准记录。

### UnlockEvent

保存隐藏解锁事件的触发记录与展示状态。

## 16. 技术路线

## 16.1 基础选型建议

首发建议：

- `Postgres` 作为主数据库
- 对象存储承载图片和音频
- 保留当前异步任务机制
- 采用 `规则 + 模型` 混合策略

不建议首发：

- 先上复杂多 Agent
- 先做全量向量检索优先
- 先开放聊天作为主入口

## 16.2 分阶段实施

### Phase 1：账号化关系系统

目标：

- 每个用户拥有独立角色
- 关系状态和记忆开始落库

### Phase 2：日记记忆闭环

目标：

- 输入日记
- 提炼记忆
- 存储记忆
- 在后续日记中稳定回响

这是首发最核心的一步。

### Phase 3：关系阶段与隐藏解锁

目标：

- 关系变化开始被感知
- 行为模板开始切换
- 隐藏事件开始触发

### Phase 4：聊天接入

在前 3 阶段稳定后，再接聊天系统。

此时聊天不是空聊天，而是建立在已有关系和记忆之上。

---

## 17. 风险与边界

1. 如果回响过于机械，会像“数据库引用”，损害真实感。
2. 如果成长只靠篇数，不靠内容深度，会过度游戏化。
3. 如果调教入口太显眼，会破坏“她先被匹配出来”的命中感。
4. 如果前端暴露太多参数，会稀释陪伴氛围。
5. 如果首发过早接入聊天，架构复杂度和调优难度会显著上升。

---

## 18. 首发范围收口

为了保证这次设计能落地，首发必须收口到以下重点：

1. 沉浸式匹配开场
2. 每用户专属角色档案
3. 基于日记的记忆采集
4. 基于日记的记忆回响
5. 关系阶段变化
6. 隐藏解锁提示
7. 互动后轻反馈与阶段性校准

首发暂不追求：

- 完整聊天
- 多角色切换
- 大而全的角色编辑器
- 高曝光成长后台

---

## 19. 最终结论

这次升级的本质，不是“给 1.0 多加几个功能”，而是把产品从“内容生成工具”推向“关系型陪伴产品”。

它的关键不在于模型更会说话，而在于：

- 她先被理解地匹配出来
- 她会持续记住用户
- 她会随着相处变得更像只属于用户的人

因此本轮设计的正确顺序应当是：

`专属匹配 -> 日记记忆闭环 -> 关系成长 -> 再接聊天`

而不是反过来。
